# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a MuJoCo simulation of the Inovance/Franzi wheeled dual-arm robot, written on this Mac and run on the lab's Linux GPU server (see "Where things run" under Commands). It is phase 1 of adapting FineART. A privileged, scripted IK expert performs a bimanual pick-and-place task (`scenes/pick_place/`) and records demonstrations:

- The base is fixed.
- Both arms grasp a box at the same time (left: blue, right: orange), lift it, place it on a wide target pad, release it, and retract.

FineART-VLA is being fine-tuned on the ten industrial scenes' Isaac demonstrations, one multi-task model, and evaluated closed-loop on Isaac (user request 2026-10-28: "训模型吧，训完评估一下，统计sr"; `fineart/`, docs/fineart.md). The old OMX 6-D policy couldn't be reused as is: its features and normalization had to be rebuilt.

Three more long tasks use the RoboSynChallenge props (`scenes/robosyn_*`, see "RoboSyn object scenes" below). A second, longer task for VLA training, dual-arm sort-and-kit, lives in `scenes/kitting/` (see "the sort-and-kit task" below). It reuses the robot scene, `Scene`'s audits and recordings, and the 16-D data contract.

The code is in packages run as `python -m <package>.<script>` from this directory: `sim/` holds what every scene shares (the derived robot scene, the policy cameras and the `Scene` episode framework), `scenes/` one package per simulation scene (see "Scenes" below), `sdk/` the stock-SDK tools, `data/` the VLA data tools, `fineart/` the FineART-VLA fine-tuning and policy server (its own env), and `robot_kinematics.py`, the shared kinematics, stays at the top level. The vendor-SDK bridge is the `simbridge/` package (see "SDK bridge" below) with an engine-free pytest suite in `tests/`. The docs are in Chinese. `README.md` is the public landing page of the benchmark (user, 2026-10-24: "这是一个benchmark"): demo previews and the scene gallery, one table row per task (content, episode length, expert result) and per industrial scene, the evaluation conventions, the policy baselines' success rates with success and failure clips (user request 2026-11-05), quick start, layout and links. Keep it short (user request, 2026-10-24): update a task's row when its expert or results change, and put details and new findings into the matching file in `docs/`:
- `robot_model.md`: the source files, the derived scene and colliders, the gripper linkage, kinematics, joint limits and servos, cameras, appearance and lighting; also the planning constraints under `config/`.
- `tasks.md`: each scene's layout, expert, success thresholds and current results, plus the shared rules and outputs.
- `sdk_bridge.md`: simbridge and the vendor SDK under `sdk_review/`. `vla_data.md`: VLA recording, conversion and export. `controller_image.md`: the offline controller-image notes.
- `benchmark.md`: the ten industrial scenes. `isaac.md`: their Isaac Sim port (`isaac/`), its mapping rules, check results and differences from MuJoCo.
- `fineart.md`: the FineART-VLA fine-tuning (data, initialization, training) and the closed-loop evaluation with its results.
- `benchmark_redesign.md`: the redesign into 11 factory tasks (user request 2026-10-25, in progress): layouts, steps, success tests, the robot's measured reach, the new props and the feasibility experiments. The props' specs are §6 of `benchmark_props.md`.
- `history.md`: every earlier version with its results and findings. Most of those run folders were deleted.
- `docs/media/`: the README's animated WebP previews and the 15-scene gallery `scenes.webp`, cut from recorded runs and scene checks; `SOURCE.json` records how. Regenerate them when a scene's look or an expert changes.

**Where things run (user decision, 2026-10-24).** This Mac only writes code: editing, Ruff, the engine-free tests and the asset builds that need macOS fonts. - `CLAUDE.local.md` (not in git) has the host, the copy's path and envs, the sync command and how to start runs there.
- After every code change, sync before running anything. The sync goes one way, from here, and mirrors the tree, deletions included. Never edit or commit in the copy: the next sync overwrites it. Commit from here.
- A sync changes the code under any batch still running there (the processes it starts later import the new code), so long batches such as datasets run from a frozen snapshot of the copy.

- The appearance caches `assets/appearance/painted/` and `wordmark/` are built here and synced: the chest and elbow text needs macOS's Avenir Next. After changing `sim/appearance.py`, rebuild them before syncing with `python -c 'import sim.build_task as b; b.build()'`. If a run there fails to open Avenir Next, the wordmark cache is stale. ## Architecture

Imports (as `from sim.<module> import ...` and `from scenes.<scene>.<module> import ...`; `robot_kinematics` is top level):
- `sim.episode` uses `build_task`, `camera_rig`, `gripper_linkage` and `robot_kinematics`.
- `camera_rig` uses `build_task`; `camera_rig`, `appearance` and `build_task` use `wrist_mount` (NumPy only, also used by `hardware/wrist_d405_mount/`).
- `build_task` uses `appearance` (which uses `fittings` and `gripper_linkage`), `gripper_linkage`, `link_hulls` and `robot_kinematics`. `gripper_linkage` needs only NumPy; `link_hulls` NumPy, SciPy and trimesh.
- `scenes.pick_place`: `task` uses `build_task` and `gripper_linkage`; `run` uses `task`, `episode` and `camera_rig`; `check` uses `task` and `build_task`.
- `scenes.kitting`: `task` uses `build_task`, `gripper_linkage` and `robot_kinematics`; `run` uses `task`, `episode` and `camera_rig`; `check` uses `run`.
- Outside the two: simbridge's MuJoCo backend and `sdk/make_sdk_program.py` build `scenes.pick_place.run.PickPlaceScene`, and `sdk/verify_backends.py` scores against `scenes.pick_place.task.GOALS`.

`sim/build_task.py` holds the shared constants: `TABLE_Z`, `PART_RGBA`, `ROOT`, and `fmt`. It also re-exports `ARM_JOINTS`, which fixes the joint order and is defined in `robot_kinematics.py`. `sim/appearance.py` defines its own `ROOT` to avoid a circular import. Each scene's layout lives in its own `task.py`.

**`scenes/`: one package per simulation scene (user request 2026-10-24: many more scenes will follow).** A scene keeps its layout and objects, its planning (the scripted expert and any sampler), its acceptance and its assets together; everything shared stays in `sim/`. `scenes/__init__.py` restates the convention.
- `task.py`: the layout and `build()`, which adds the scene's objects to `build_task.build()` and returns `(root, report)`. Name object bodies `<name>_part`: `Scene.robot_bodies` excludes that suffix.
- `run.py`: the `Scene` subclass, the expert and the episode CLI.
- `check.py`: the scene's acceptance.
- `assets/`: meshes, textures and maps that only this scene uses, referred to by absolute path (`Path(__file__).parent / "assets"`), since the compiler's meshdir is the robot's. Third-party assets that may not be published stay out of git: the repository is public.
- Scenes import `sim` and `robot_kinematics`, never each other.
- The move into `scenes/` (2026-10-24) changed no run: pick and place and kitting seeds 0 and 1 reproduced `scene.xml`, `trace.json`, `trajectory.npz` and `episode.json` bit for bit, and the stock-SDK acceptance passed.

**The industrial benchmark (docs/benchmark.md, user request 2026-10-24).** Ten scenes, three easy, four medium and three hard: `tote_transfer`, `panel_operation`, `tray_push`, `parcel_sorting`, `tote_carry`, `shaped_kitting`, `lidded_tote`, `palletizing`, `cnc_tending` and `precision_insertion`. On 2026-10-25 (user request) they were reworked to what this robot can do: the workbench rose to 0.90 m, the scene check gained a grasp probe, and parcel sorting, palletizing and precision insertion were redesigned and carton_carry replaced by `tote_carry`; docs/benchmark.md lists every change and why.
- Each has `task.py` (layout, `build()`, `KEY_POINTS`) and `check.py`. All ten have experts (tote_transfer first; the other nine written by parallel agents on 2026-10-25, each validated on 20 or more seeds with the hull colliders and the contact audit; docs/benchmark.md "专家"). Recordings start in the default posture (`tabletop.start_home`). Episodes split into subtasks (Experiment rules): five experts that had both arms working at once now work one arm at a time, and tote_carry's arms go back one after the other, which made those six episodes 15–135% longer (parcel sorting 65 → 130 s, cnc_tending 156 → 180 s). All ten then passed seeds 0–19 together on one frozen snapshot, with `data.subtask_check` (2026-10-25). Each has `run.py`, a seeded `sample_episode()` that `build(spec)` takes (`build()` alone is the nominal layout, for the scene check) and a success test. Each `run()` takes `engine`, so the same expert runs closed-loop on Isaac. Layout changes the experts needed: tote_carry's target 1 cm over, cnc_tending's hand-over stand; several experts tilt the hand 30–35° instead of 45° to keep the wrist off the chest. The user judged on 2026-10-25 that many of these tasks lack meaning; `docs/benchmark_redesign.md` (another session's draft, awaiting review) replaces seven of them with real line tasks. After the switch to wheel_robot_26.8.16_3 the same agents redid all ten on it. Each passes the scene check, MuJoCo seeds 0–19 and Isaac seeds 0–2 closed-loop, with subtask_check OK and no collisions (`outputs/<scene>_urdf3/`; docs/benchmark.md has the table).
  - They rest on two PhysX rules. A held part doesn't creep down the jaws on PhysX, so every set-down re-measures the part (privileged) and lets go within 0.5 mm of the support. A phase that ends within 0.5 mm of a support isn't a carry phase, since PhysX pairs within 0.5 mm count as touching.
  - Two helpers in shared code were stale and were left alone until the new-model Isaac collection was done: robot_kinematics.ik()'s built-in seeds used the old joint convention, and tabletop.TIP said 17 mm where the fingertips reach 13.4 mm past the pads. Both were fixed afterwards (2026-10-25), and with them the default posture moved about 2° along the elbow swivel. That batch (`inovance-fineart-urdf3-data`, 99 of 100 episodes) stays valid data but is no longer reproducible seed for seed from the code. Several scenes still carry their own IK seeds or a local 13.4 mm.
  - On 2026-10-27 (user request: 200 Isaac episodes per scene, "注意随机化") one agent per scene widened its sampler. Parts move by centimetres and turn by tens of degrees (round ones to any yaw). Totes, trays, rails and fixtures move and turn on the bench too, as far as reach, the expert's reliability and the head and body D435 views allow. Each task version went up by one. Each scene passed the scene check, MuJoCo seeds 0–39 (33–40 of them planned on the first draw) and Isaac seeds 0–2 (`outputs/<scene>_rand/`). docs/benchmark.md "随机化放大" has every range and what limits it.
- Their props were built in Blender by Codex from `docs/benchmark_props.md`: `tools/blender/` holds the build scripts, `assets/props/<id>/` the output (OBJ parts, baked textures, convex collision pieces, `prop.json`). Rebuild props there, never by hand-editing the OBJs.
  - The redesign's 29 new props, the rebuilt foam kit tray and an IMC carton variant (§6, build scripts `build_task14`–`18`) were built on 2026-10-25 by Codex on the pro6000, in five parallel jobs, each in its own copy of the tree, then pulled back here and checked: the validator, a MuJoCo load-and-settle test, joint and conveyor tests, and renders. Conveyor rollers are separate parts on continuous hinges; the scene drives them with velocity actuators. Buttons are 40 mm caps on sprung slides, lamps untextured parts whose colour the scene sets.
  - Static props with moving parts need `collision_exclusions` between the frame and each moving part: MuJoCo doesn't filter parent-child contacts when the parent is welded to the world.
  - `prop_assets.add()` gives every limited joint the contacts' `solref`/`solimp` (2026-10-25). With MuJoCo's defaults the 20 g button caps ran several times past their 4–6 mm travel under a 10 N push; a push ramped to 10 N now overruns 0.2–0.5 mm, and knobs and lids stop on their limits. A part's `contact_priority` becomes geom priority: the flow lane's 0.03 slide must beat a tote's 0.4, since MuJoCo otherwise takes the larger friction.
  - The penetration audit only catches more than 1 mm. Unintended light contacts (an arm brushing a cart, a carried tote clipping the next one) are what `Scene`'s contact audit catches (see "the episode"); every run applies it.
  - `tools/blender/support_task16.py` is Task 16's helper module; it was `task16_support.py`, which `.gitignore`'s `tools/blender/task[0-9]*` hid.
  - Every build script ends with `prop_lib.finalize_assets()`, which runs `compact_props.py`: textures at most 1024², shared atlases deduplicated, OBJ coordinates rounded. `assets/props/` is about 90 MB without the `source.blend` files (54 MB).
  - `shaped_kitting` loads the foam tray's `light_grey` variant (user request 2026-10-24): the cameras can't make out the pockets in the black foam.
  - On 2026-10-25 the workbench (900 mm), the foam tray (pockets 4 mm per side), the sort bin (200 × 240 × 100, zones A–D), `parcel_box_s` (label D), the pattern sign (`plan_04`), the bearing (collision a ring with the bore open), the pin fixture (`c100`) and the new `bearing_shaft_fixture` were rebuilt here with Blender 5.2.0, by editing their build scripts (the label and sign artwork needs macOS fonts). `compact_props.py` now checks UVs with the rounding it writes them with (np.round and f"{v:.4f}" differ on a decimal tie).
- `sim/prop_assets.add()` loads a prop: one `_part` body per part, nested as `prop.json` says, every part in the prop frame. Visual geoms are group 2, massless and contact-free. Convex collision pieces are group 3, with the part's mass spread by volume. Joints follow `prop.json`. A free prop's joint is `<name>_part_joint`, the name `sim.tabletop.ObjectScene` looks up. Joints also take `prop.json`'s `solreffriction`/`solimpfriction` (the lidded tote's static hold; PhysX has no counterpart). A jointed part starts at its `recommended_initial_qpos`, or at `add(initial={part: value})`: its body is posed there and the joint's `ref` set to it, so `qpos0` is the start and ranges keep the prop's coordinates. Detents, latches and the CNC jaw clamp are not modelled.
- `sim/workcell.industrial_cell()` swaps build_task's floor and table for the factory floor, the workbench (top at `BENCH_Z`, 0.90 m since 2026-10-25, 0.10 above `TABLE_Z`; front edge x = 0.20) and a fence-and-rack background behind the overview camera.
- `sim/bench_check.py` settles a scene for 4 s under the Scene audits, checks free-prop drift and reaches every key point with the shared IK (top-down or the 45° `sim.tabletop.grasp_rotation`), and renders `preview.png`; the instruction comes from the build report. The IK tries the hanging arm, then the default posture, then the arm's key points solved before, as an expert chains its moves. After the IK seeds moved to the new joint convention, shaped_kitting's gear pocket solved only from the default posture, and its release point only from the pocket.
  - Key points are grasp-site targets (the open pads' centre, backed off by `contact_drop` as the experts do). Optional keys: `yaw` (top-down hand about z; 0 closes the jaws along x), `psi` (45° grasp azimuth), `width` and `ignore`.
  - A point with a `width` gets the grasp probe: the object must fit the 95 mm jaws with 4 mm per side, and the arm, posed there by the IK with its gripper open as `grip_open(width)` opens it, may touch nothing but the robot (a static contact test in a copy of the settled state; `ignore` lists bodies moved by then, such as a lid or door opened first). Points the hand is meant to touch (buttons, push faces) carry no width.
  - Reach alone had passed palletizing and parcel sorting with objects wider than the jaws. On 2026-10-25 all ten passed with every grasp probed.
- Layout limits (bench at 0.90): a top-down grasp reaches x ≤ 0.45–0.48 at bench height (0.37–0.41 on the old 0.80 bench), the 45° grasp 0.57–0.61. Each arm stays on its own side of y = 0, and low near the midline neither reaches (x 0.30, z 0.74: the left arm's 45° grasp stops at y 0.05). The head can pitch only 30° down, so the reachable bench fills the bottom fifth of its image; the body D435 sees it better.

**`isaac/`: the Isaac Sim port (docs/isaac.md, user request 2026-10-25: the industrial benchmark first).** A scene is ported from its compiled MuJoCo model, so its layout, colliders, masses, joints, gains and cameras are the MuJoCo scene's; PhysX and RTX replace MuJoCo's physics and renderer. Two interpreters share the work:
- `export.py` runs in the project env. It builds the scene as `sim/bench_check.py` does and writes `model.json`, `arrays.npz` (the compiled mesh arrays) and `textures/` (2D textures, rows flipped for USD's bottom-up texture coordinates). It also runs the MuJoCo scene check into `mujoco/`, the reference.
- `stage.py`, `runtime.py`, `check.py`, `engine.py` and `episode.py` run in Isaac Sim's own Python through `isaac/run.sh`. Import `stage` and `engine` only after `runtime.start_app()`: they need pxr's PhysX schemas.
- `stage.py` maps the model:
  - A body that moves on its own becomes a rigid body, the bodies welded to it merged in. Each finger's two joints become a chain of two bodies, and the wheel and steering joints are welded.
  - Each tree with joints is one fixed-root articulation. The linkage's 26 coupled joints get stiff drives, whose targets `Runtime.step()` sets every physics step from the finger slides through MuJoCo's quartic polynomials (PhysX mimic joints are linear).
  - Robot links ignore gravity, which stands in for the feedforward. contype/conaffinity become collision groups, contact exclusions filtered pairs, and friction combines by the maximum.
  - Not ported: frictionloss (PhysX joint friction is a coefficient of the joint force) and contact priority (tray_push's 0.25 tray on the 0.6 bench becomes 0.6).
  - USD angular drive gains are per degree; PhysX parses them back as the SI gains (checked).
- `check.py` mirrors the MuJoCo scene check: the 4 s settle with the head ramp, free-prop drift, the deepest contact, previews, and `compare.png` with MuJoCo's preview. It also poses the robot in a random test posture and compares every robot body with MuJoCo's FK.

**`robot_kinematics.py`: the one shared FK/IK ("real follows sim", user decision 2026-10-24).** Cartesian goals are solved here on the host; the simulation and the real robot both receive joint commands only (`MoveJ`, joint teleop). The controller's own IK, `MoveL` and Cartesian teleop are deliberately unused. simbridge's IK/Fk endpoints call this module; `simbridge/sdk_kinematics.py` only converts SDK conventions.
- FK and Jacobians come from Pinocchio (user decision, 2026-10-24). The module needs NumPy, SciPy, PyYAML and pin, all in the `inovance-fineart` env, but no physics engine. Keep MuJoCo and `build_task` out of it.
- Pinocchio's model is the source URDF (`wheel_robot_26.8.16_3.urdf`), its root stood up by `ROOT_IN_BASE` (the URDF's root frame lies on its back, x up) on the base frame `BASE_HEIGHT` (87.3 mm) above the floor, where franzi.xml's base stood, with an operational frame per `{side}_grasp` tool point from `config/robot/franzi_sdk.yaml` on the gripper link. Leg and waist joints come from `body` (`BODY_JOINTS`); every other joint is neutral. FK equals the scene's to 1e-9 m.
- `Kinematics.ik()` is the expert's IK: multi-seed `least_squares` on position (×10) and the rotation vector to a fixed world-aligned grasp orientation, inside the aligned limits.
  - The seeds are the live arm pose, then three fixed postures in wheel_robot_26.8.16_3's convention (wheel_robot_4.0's seeds times its SDK signs, fixed 2026-10-25). Left in the old convention, their elbows sat outside the new range, clipped onto its bound; each alone solved 21–36% of a grid's reachable targets, the mapped ones 44–98%. The old set's union only looked better on fingers-down targets because one old seed found flipped-arm solutions (shoulder pitch near 2.9 rad) high by the body.
  - The Jacobian is exact: Pinocchio's frame Jacobian, with `Jlog3` for the rotation rows. It lands within 5e-8 rad of the old finite-difference solutions, and is 6× faster (single target about 6 ms, chained waypoint 1.3 ms).
  - When chaining waypoints (`near=`), a residual `(q - near) * 0.002` keeps the redundant elbow swivel near the previous solution; without it the arm visibly wobbled along straight moves. 0.02 is too strong (the approach IK becomes infeasible).
  - `line()` gives the 1 cm waypoint chains, and `to_sdk()`/`from_sdk()` map URDF ↔ SDK joint values.
  - `Kinematics(margin=...)` keeps solutions that far inside the aligned limits. The default is `PLANNING_MARGIN`, 2° (user decision, 2026-10-24). With the old 0.0001 rad, the pick-and-place approach parked both wrist pitches 0.065° from the controller's −60° limit, where tracking overshoot on the real robot could trip its soft limit. At 2° they stay 2.06° away, and the grasp orientation is unchanged.
  - simbridge's controller-emulating IK endpoints pass the SDK position margin plus 0.0001 (see the SDK bridge). The kitting expert uses 10 mrad and its sampler 20 mrad: planned on a limit, the shoulder roll overshot the 2 mrad audit by up to 12 mrad, and its inner cells put the shoulder roll within 2° of its limit.
- `controller_rates()` returns the arm velocity and acceleration limits stored in the controller image, plus its default 30% speed ratio; `Scene.move` keeps the expert within them. They are not verified on hardware.
  - A seed whose rotation error reaches π (no finite `Jlog3`) is skipped instead of raising `ValueError`.
- Joint limits are `controller_ranges()`; `build_task.align_joint_limits()` writes the same numbers into the scene.

- Painting. Each visual mesh in `RECIPE` is split into connected CAD components, sorted largest first. Each component gets a `PALETTE` material by index, with `"rest"` covering the others.
- `"parts"` rules repaint whole components chosen by bounding-box size. Mirrored arms share these sizes, though their index order can differ; the gripper's jaw blocks, pins and screws use them.
- `"faces"` rules repaint regions within one component: the thigh crossbar, the upper-arm grille pad, and the shoulder and inner elbow caps. A material of `None` drops faces; the head D435 uses this to drop the URDF camera box that is merged into its bracket.
- `attach_real_cameras()` swaps the URDF camera boxes for the official RealSense meshes in `assets/appearance/cameras/` (see each `SOURCE.json`):
  - D435: Menagerie's coloured parts, rotated 90° about z and offset by `D435_ALIGN`, so the left IR imager is at the sensor origin and the glass is 4.2 mm ahead, as in realsense-ros.
  - D405: realsense-ros `d405.stl` at the same frame, carried onto the wrist D405 adapter like its camera (`wrist_mount.sensor_pose`).
- The wrist D405 adapter (`hardware/wrist_d405_mount`, user request 2026-10-25) holds each D405 on its gripper's camera strip: `attach_wrist_blocks()` adds the printed part's STL, black, on the strip's top pad (the same part on both hands, unturned).
- The camera origins sit behind the glass, so the policy cameras rely on the 45 mm render `znear` not to see their own housings.
- `attach_chest_slot()` fills the chest camera slot (`CHEST_SLOT`, in the body D435 sensor frame) with a pearl bezel plate and a tinted 82 × 10.5 mm window, 0.4–1.0 mm ahead of the glass. The shell's opening (85.1 × 20.8 mm) otherwise shows the whole D435 front, while the real robots show a narrow dark window. These are inline meshes inside `znear`, so the body camera never sees them.
- The face visor has no camera window. The head D435 sits 16–20 mm behind it, inside the 45 mm `znear`. Removing the whole visor, or the chest decal, from the render changes 0 pixels in all four policy cameras. A cut window with a rim and shroud was built and then dropped at the user's request (2026-10-24), because it changed nothing in the recordings.
- Rendering is deterministic, but recorded MP4s are not a pixel-level comparison. A visual geom that changes `m.stat.extent` moves a few shadow pixels, and H.264 spreads that to roughly 0.5% of pixels. Compare raw `mujoco.Renderer` frames instead.
- Cap rules keep only faces wholly inside a CAD vertex ring and connected to the cap centre.
- The outer elbow cap's triangles cross every face-level cut, so it is drawn by a texture instead: a conformal decal on the pearl elbow mesh with a black disc and the white logo.
- URDF sensor sites are moved to group 4 so their marker spheres don't render; `camera_rig.assert_mounts()` still uses them.
- Each `(mesh, material)` group becomes one visual geom. It keeps the original geom's `pos`/`quat` and has an `inertia="shell"` mesh asset. If the CAD changes, `paint_groups` asserts rather than leaving a component unpainted.
- The gripper recipes' `"table"` (`gripper_linkage.face_table`) gives each face of the merged gripper surface its moving part and finish: the links and jaw blocks go into the bodies that move them, offset by those bodies' origins; jaw blocks and pins are aluminium and the jaw screws red, as wheel_robot_4.0 painted those parts.
- Caches live in `assets/appearance/{painted,wordmark,fittings}/`. The paint key covers only the source STL bytes, the gripper face table and `PAINT_VERSION`, so bump `PAINT_VERSION` whenever a face rule changes. Older files directly under `assets/appearance/` (`head_*.stl`, `head_parts.json`, `inovance_wordmark.png`) are unused leftovers.
- The chest decal is a copy of the torso front-shell triangles (component 2) lifted 0.4 mm along MuJoCo's compiled normals. MuJoCo ignores texture alpha, so the texture background is `PEARL_SRGB`, derived from `fa_pearl`, and only the print shows. Don't add face rules on the front shell near the print: the decal's normals must match the pearl geom's.
- The chest print is the factory robot's, from top to bottom: INOVANCE (`WORDMARK`), "Powered by", FMC³ and a tracked ROBOTICS line (`FACTORY_PRINT`). It was measured on frontal factory-video frames, using the INOVANCE width as the ruler.
  - The FMC³ letters are drawn from `FMC3_GLYPHS`, read off a 30-frame stack of the factory video: a floating bar over a Γ, a V-shaped M, a C with two dot eyes, and a small 3 on the cap line.
  - `assets/franzi_source/assets/fmc3_logo.png` is a different logo version (comb M, one square in the C). Only its 3 is used.
- `sim/fittings.py` adds the `fit_*` parts the CAD lacks: the lower-back ribbed panel (a harmonic fill of the opening's rim), the upper-back e-stop, ports and lights, the thigh back cover, and the base light strips. They are placed on surface fits of the shells and reference `PALETTE` material names only.
- Fonts: the chest and elbow text uses macOS's Avenir Next, so its caches are built on the Mac (see "Where things run"). Overlay text in recordings and preview sheets goes through `sim.episode.overlay_font`: Arial on macOS, DejaVu Sans on Linux.

**`sim/camera_rig.py` and `sim/camera_rig.json`: the policy cameras.**
- `POLICY_CAMERAS` are the head and body D435 and the left and right wrist D405. Each is attached to the URDF sensor site of the same name.
- Camera axes are the site frame, rotated by the optical roll from the JSON, then 180° about x. The flip is needed because the sensor frame looks along +Z while MuJoCo cameras look along −Z. `assert_mounts()` checks the result after forward kinematics.
- The D435 rolls are −90°. The wrist D405 rolls follow the CAD: left 0°, right 180° (user decision, 2026-10-24).
  - With them, image right runs along the jaw axis and image up points outboard.
  - The reasoning: each D405 is held by its rear M3 pair, which is parallel to its stereo baseline and, in the wrist CAD, runs along the jaw axis. The user confirmed that on the real robot the fingers appear left and right.
  - The old −90° put the fingers at the top and bottom of the image.
- The intrinsics are uncalibrated simulated pinholes.
- Change a camera's view only by moving joints. For example, the head gaze is a `head_pitch_joint` actuator command in `sim/episode.py`. Never re-aim a camera or detach it from its site.
- Exception: the wrist D405s sit on the wrist D405 adapter (`"mount": "wrist_block"` in `camera_rig.json`). wheel_robot_26.8.16_3 holds its D405 on a strip beside the housing, near the flange, looking straight down the hand, where the housing hides the jaws; the adapter, on the strip's top pad and its two screws, holds it 38 mm further down the hand and tilted 20° toward the jaws (user request 2026-10-25: the whole gripper in view). That is the pose relative to the jaws of the tilted block of 2026-10-24 on wheel_robot_4.0's gripper (the user's reference model): the lens 65.5 mm beside the jaw plane and 88 mm behind the grasp point. `sim/wrist_mount.py` reads `hardware/wrist_d405_mount/params.json`; the camera pose, the D405 mesh, the adapter's visual and its colliders all come from that module; change them only together. `assert_mounts()` checks camera = site × the adapter's bracket (`bracket_in_site` in the camera metadata).
- The world cameras added in `sim/episode.py` (`overview` and others) are for display only and are never policy inputs.

**`sim/episode.py`: the episode (`Scene`), shared by every scene.**
- `Scene` installs the cameras, compiles the model, sets the render `znear` to 45 mm so each camera sees past its own housing, and writes the result to `scene.xml`. Two overrides are applied only to the compiled model and are missing from `scene.xml`: the finger actuators get kp 1500 and a force range of ±6 N, and the `TORSO_SERVOS` (calf, thigh, waist pitch and yaw) get velocity feedback `kv` for a damping ratio of 0.7 at the start posture. Without `kv` the source servos (kp 6000, damping 5, ζ ≈ 0.01) let the upper body rock at about 1.5 Hz after every arm move (user decision, 2026-10-24). Don't raise it to ζ = 1 without re-testing: before the 2° planning margin, the expert parked the wrist pitch on its bound, and the changed posture tripped the 0.002 rad limit audit.
- Physics runs at 500 Hz and control at 25 Hz. On every 20th physics step the code appends one trace sample (the measured state plus the action about to be applied), renders one frame per video, and updates the stable-frame counter. Joint goals are held constant between control ticks.
- The robot is driven only through position-actuator `ctrl`, plus gravity compensation via `qfrc_applied = qfrc_bias` on the arm DOFs, on the `TORSO_SERVOS` and `HEAD_SERVOS` DOFs, and on the gripper linkage's coupled joints (`Scene.held`).
  - On kp alone the leg and waist servos sagged up to 7.5 mrad each (about 1.3° in all) with the arms forward, and the head pitch 3.8 mrad. That shifted the head and body cameras, and put the hands about 9 mm off when expert joint targets were replayed in PyBullet.
  - With the feedforward the error is 0 at rest, and at most about 1 mrad during moves (user decision, 2026-10-24). Head pitch still lags about 5 mrad while its 1.5 s gaze ramp is moving.
- After every physics step, a penetration over 1 mm or a joint-limit overshoot over 0.002 raises `RuntimeError` and ends the episode.
- The contact audit (user request 2026-10-25: no collisions). `audit_contact()` logs every touching contact of a robot body except the base, wheels and steering links on the floor, and a hand (a `wrist_roll` link and everything below it) on something movable (`body_weldid` not 0: free objects, buttons, lids, doors). Robot-robot contacts count too. `collisions()` lists each pair once, with the first time and phase, the physics steps it lasted and its deepest penetration. `ObjectScene` adds held objects touching anything but the robot during its `CARRY_PHASES`. A run with any is not a success: `run_episode`, pick and place's `main()` and kitting's `run()` all check this. `isaac/engine.py` feeds PhysX's touching pairs through the same `audit_contact()`.
- `check_physics()` runs after every step and raises `PhysicsError`, a `RuntimeError`, when the simulation itself breaks. That means MuJoCo's bad-state warnings, which `mj_step` answers by silently resetting the state; its full contact or constraint arena, which drops contacts; a non-finite state; or a free object faster than 10 m/s or 200 rad/s (none falls more than 1.3 m, about 5 m/s). The runs record such an episode with `"void": true`: redraw the seed rather than count it, as RoboDojo does with broken PhysX environments.
- `Scene.ik()` delegates to `robot_kinematics.Kinematics.ik()`, passing the live arm pose and leg and waist joints; it never touches the live state. `sdk/make_sdk_program.py` calls it. Change IK behaviour in `robot_kinematics`, not here.
- `move()` follows a quintic minimum-jerk profile. By default it interpolates straight between joint-space IK solutions. With `linear=True` it runs through `Kinematics.line()`: IK waypoints 1 cm apart on the Cartesian line, each chained to its predecessor's branch. The pick-and-place expert uses `linear=True` for align, lift, transfer, place and retract: near the edge of the arm's reach, plain joint interpolation swings the hand about 2 cm forward mid-descent, and a finger lands on the box.
- `move()` then lengthens each move (`stretch()`) until its 25 Hz arm goals stay within `RATE_HEADROOM` (0.9) of `controller_rates()` scaled by the default 30% speed ratio. A replay on the real robot at that ratio is then not clipped (user decision, 2026-10-24).
  - In pick and place only ready and approach stretch: its reference episode went from 24.5 s to 29.9 s, with peaks at 0.90× (velocity) and 0.48× (acceleration) of those limits.
  - A move's `speed=` (used by the kitting task) applies first. Moves already within the limits keep their duration.
- The thigh's straight-leg target of 0 sits on its lower joint limit, so fast arm swings can push it past the 0.002 limit check. That is why pick and place's final retract takes 3 s.
- `Scene` writes `scene.xml`; each scene's `run.py` adds `summary.json` (result, physics stats, data contract, and collision, appearance, and camera metadata), `trace.json`, and `trajectory.npz`.
- `move(joints={side: q})` moves an arm to a joint goal instead of an IK target.
- `prepare(targets, grips)` takes a starting posture before the recording (user request 2026-10-25: an episode starts in the robot's default posture, both grippers held up and the head down, not with the motion into it). The servos move the arms there while the gaze finishes (3.3 s), and it holds until no arm, torso or head joint moves faster than 5 mrad/s for 12 ticks. Recording is off meanwhile (`recording`, also in `isaac/engine.py`), and `clock()`, the trace's `t` and `duration_s` count from its end, a control tick (`t` = 0); `summary.json` gives the unrecorded time as `prepare_s`. Without it nothing changes (pick and place's 18 trajectory arrays checked bit for bit).
  - `prepare(..., lift=True)` first raises each hand to the target's height above where it hangs, keeping its orientation. It then moves to the IK solution found from the hanging arm, so the final joints are the same as without the lift. Both moves are in joint space. A straight line from the straight hanging arm starts beside a singularity: its waypoints jumped, and `stretch()` made `prepare_s` 48 s instead of 10.6 s.
  - On wheel_robot_26.8.16_3 the hand hangs right under the shoulder, where the arm can't hold it up at the ready height (0.99 m): the lift then takes the least step toward its target, in tenths of the way, that the IK reaches (5 cm at `READY`).
  - `tabletop.start_home` is the default posture: both hands at `READY` with the fingers down, the jaws 85 mm open (`HOME_OPENING`), the head at the gaze. Raised with the jaws fully open, a finger sat on its open limit and overshot it by 2.3 mm. It uses `lift=True`: swung from hanging in joint space, both fingertips brushed tote_transfer's bench (0.17 mm, found by the audit). Its final joints equal `kin.ik(side, READY[side], np.zeros(7))`, which tote_transfer's sampler plans from. It is a stand-in until the real robot's default joint values are known.
- On a mobile base (`build(mobile=True)`), `drive(x, y, yaw)` moves it on a straight line while it turns, the arms holding their joint goals, within the chassis SDK's velocity range (0.5 m/s, 0.2 rad/s; `publish_vehicle_control`) and accelerations chosen here (0.5 m/s², 0.5 rad/s², the SDK documents none), with the 0.9 headroom. `ik()` and `move()` take world targets and convert them into the base's start frame, where the shared kinematics works (`to_base`). The three wheel units steer and roll along, a swerve drive (user 2026-10-25: not sliding like mecanum wheels): before a drive they turn to where it starts (`STEER_RATE`), then each steers along its own velocity and rolls at its speed over the wheel radius. The base still moves on its planar joints; the wheels carry no load. The units' positions come from the start pose's joint anchors (their bodies sit in `base_link`'s turned frame). The full log adds `base_pose`, `base_goal` (world, from the start), `base_velocity` and `base_command` (forward, left, turn, in the base frame, as the SDK takes them), and `wheel_steer` and `wheel_rate`.
- The waist and head take goals too (user request 2026-10-25: control the waist, record everything). `turn(yaw)` turns the waist while the arms hold their joint goals, within the controller's waist limits (30 deg/s, 40 deg/s², 50 deg/s³) at its 30% ratio with the 0.9 headroom; `look(yaw, pitch)` points the head at the full head rate, like the gaze ramp, which runs until a scene looks. With neither called, the physics is bit-identical to before (pick and place, kitting seed 0, lab seed 0 and tote transfer seed 0 checked: trace, legacy arrays and scene.xml).
- Every control tick also logs the full state (`full_arrays()`, added to `trajectory.npz`): `FULL_NAMES` (the 16-D contract, then calf, thigh, waist pitch, waist yaw, head yaw and pitch) as `state_full`, `action_full`, `velocity_full` and `effort_full` (servo plus gravity feedforward; gripper squeeze force), `finger_qpos`, `eef_pose` and `camera_pose` (world, wxyz), and the world state for evaluation only: `object_pose`, `object_velocity`, `prop_qpos` and `contacts.json`. `VIEWS` names the 16-D (`arms16`) and 17-D (`waist17`, plus waist yaw) training subsets. `summary.json` describes it under `contract.full`.
- A recording also writes `depth_<camera>.mkv` (mm along the optical axis) and `segmentation_<camera>.mkv` (instance ids, `segmentation.json`: 0 nothing, 1 the robot, then one per body), FFV1 gray16le, one frame per trace sample (`RECORD_DEPTH`). The vendor SDK documents no waist motion command (MoveJ and joint teleop take sides 0, 10, 15), though its side enum names Waist = 20 and Head = 30 motion modules.
- `--record` adds `expert.mp4` (overview plus wrist insets), `cameras.mp4` (2×2 mosaic of the policy cameras), and one 640×480 MP4 per policy camera. All videos are 25 FPS with exactly one frame per trace sample.
- The base `Scene` builds the robot scene alone: it samples no objects, tracks nothing and never completes. A scene subclass overrides `build_root()` (scene tree and report), `object_info()`, `sample()` (one trace record), `track_objects()` (per-step grasp evidence, in `lift_evidence`) and `complete()`; `PickPlaceScene` and `KitScene` do. `ik(rotation=)` and `move(rotations=)` take a hand rotation per arm. `move(speed=)` times the waypoints by joint travel (largest joint step) and stretches the move until no joint's peak command rate exceeds `speed`. The defaults keep the pick-and-place expert bit-identical (trajectory, trace and scene.xml checked).

**`scenes/pick_place/`: the pick-and-place task.** `task.py` holds `SOURCES`, `GOALS` and `PAD_DROP` and adds the two 45 mm boxes (`left_part`, `right_part`) and their wide target pads to the robot scene. `run.py` holds `PickPlaceScene` (per-side grasp evidence and the success test) and the expert; `check.py` is the acceptance. simbridge's MuJoCo backend and `sdk/make_sdk_program.py` both build this scene.
- `expert()` starts in the default posture (`tabletop.start_home`), then the left arm and after it the right each run three subtasks (since 2026-10-25, the subtask rule): pick up the box (approach, align, grasp, lift), put it on its pad (transfer, place, release), move the arm back (retract, finish); the other arm holds. Along the way it checks that both jaws touch the box and that it is lifted high enough. The subtask text and the stage name become the trace's `subtask` and `phase`. Reference run on wheel_robot_26.8.16_3 with the fixed IK seeds: `outputs/pp_seeds_rec/` (43.3 s, 0.099 mm, no collision, both boxes 0.30 mm from their pads, `check.py` and `data.subtask_check` pass; `outputs/pp_urdf_rec/` before the fix). Before, both arms worked at once (30.0 s, `outputs/expert_wrist_block/`, wheel_robot_4.0).
- It grasps and places `PAD_DROP` (14.5 mm, the pad drop on the 45 mm boxes) higher than the box centre, so the closed fingertips stay 14.1 mm above the table, as before the linkage model. Without it they pressed about 0.4 mm into the table.
- `check.py` re-checks a recorded run folder:
  - the success thresholds
  - the structure of `scene.xml`: no `<weld>`, exactly 2 freejoints, mesh colliders on the wrists (counted across the wrist's subtree, where the linkage hulls ride) and fingers
  - each video's frame count, FPS, and width
- Video names come from `contract.cameras` in each run's `summary.json`. Runs from before the 4-camera rig, such as the first demo `outputs/expert_local_bright/` (with `front`, `left_wrist`, and `right_wrist` videos; deleted since), therefore still verify.
- The success thresholds are written in four places: `PickPlaceScene.complete()` and `main()` in `scenes/pick_place/run.py`, `scenes/pick_place/check.py`, `sdk/verify_backends.py`, and `docs/tasks.md`. Change them together. Since 2026-10-25 `main()` and `check.py` also require no audited collision; `sdk/verify_backends.py` scores the SDK run's object poses and has no audit.

**`scenes/kitting/`: the sort-and-kit task (`task.py`, `run.py`, `check.py`).** Each arm moves the three parts on its supply mat into the three cells of its kit tray, each part into the cell of its colour. Each kind of part has its own colour (blue cube, orange cylinder, green hex prism; user request), and each side gets one of each, so each tray has one cell per kind. In each of three rounds the left arm moves one part and then the right arm one (single-arm subtasks since 2026-10-25: pick up the part, put it in its cell; at the end each arm moves back on its own), so an episode takes 110–163 s (63–110 s with both arms at once, at Scene.move's time-scaling to the real controller's default 30% speed).
- Layout per side: kit tray at x = 0.38 (both policy cameras see it), supply mat at x = 0.48, slots at |y| = 0.13, 0.25, 0.37. The spacing comes from the gripper housing, which at the kitting grasp spans about 85 mm to either side of the grasp point and 65 mm behind it at grasp height. Four slots per side at 85 mm pitch put the housing into the neighbouring part in round one; hence 120 mm pitch and rows 100 mm apart.
  - The slots were at |y| = 0.10, 0.22, 0.34 until wheel_robot_26.8.16_3: its longer gripper put the forearm into the chest over the inner cell, up to 17 mm into the torso's hull at the old retreat along the approach and 8 mm with the hand retreating straight up. 30 mm further out, every arm link keeps 11 mm from the torso over seeds 0–19; the outermost cell still shows 672 pixels in the body camera.
- `grasp_rotation(side, psi) = Rz(psi) Ry(-45°) Rz(±90°)`: the hand approaches 45° forward and down. The fingers slide along the wrist_roll link's local x, so the 90° roll (left −, right +) makes them close horizontally along y and keeps the wrist D405 on top of the hand. The opposite roll reaches as well, but it hung the camera underneath, toward the robot (user correction). psi is the part's yaw folded by its kind's symmetry (90° for the cube, 60° for the hex prism; both start within ±10°), 0 for the cylinder. The grasp point is 35 mm above a part's base; the fingertips reach 13.4 mm past it along the fingers. The top-down grasp reaches only x = 0.40 at part height, this one x = 0.44 across y 0.03–0.45.
- `sample_episode(seed)` draws per side the order of the three kinds on the mat and in the tray, slot jitter (±6 mm in x, ±4 mm in y), the yaw of cubes and hex prisms, and one of four instruction wordings. It IK-checks every 1 cm waypoint of the expert's moves at `SAMPLE_MARGIN` and redraws until the episode plans.
- `build(spec)` is `build_task.build()` plus the tray and mat boxes, the coloured cell frames (drawn only: contype and conaffinity 0) and the parts. The hex prism is the vertex-only mesh asset `kit_hex`, whose convex hull MuJoCo builds. Part bodies are named `<name>_part` so that `Scene.robot_bodies`, which excludes by that suffix, stays right.
- The expert reads measured part poses at the start of each round (privileged). Its rules, each learned from a failure:
  - `READY` is the two-part expert's point with the kitting rotation. A ready point over the tray clipped the table edge on the way up.
  - The episode starts in the default posture (`tabletop.start_home`: fingers down at `READY`); each arm turns into the kitting grasp in place before its first part (the sampler plans from the same pose, `task.ready_pose`). Swung straight into the kitting grasp, a fingertip brushed the table (0.32 mm), which the linkage turned into a jaw driven shut.
  - After letting go the hand rises straight up from the cell (`key_poses`' `retreat`), not back along the approach, which brought the forearm to the chest; the open jaws clear the part by 12 mm either side.
  - `key_poses` backs every grasp-site target off along the approach by `contact_drop(width)` (15.1 mm), so the dropping pads still close at the grasp point.
  - Every move after `ready` is a straight line. A joint-space approach swept a hand through a part already in the tray.
  - The grippers never open fully (`grip_open` is the part width + 24 mm). Open fingers sit on their joint limits, and once the hand tilts, gravity along the slides (fingers get no feedforward) pushed them 2.9 mm past.
  - IK at `LIMIT_MARGIN` (10 mrad) and moves at `speed=SPEED` (0.6 rad/s). The inner slots push the shoulder roll onto its limit, and fast joint-space jumps there overshot it.
- Success is `KitScene.placements()`: every part in a cell of its colour (±15 mm in x and y), upright (≤ 15°), seated (±3 mm), still (< 0.025 m/s), clear of the robot, one part per cell, held for at least 15 ticks, each part with at least 100 airborne bilateral grasp steps, and no audited collision (since 2026-10-25; seeds 0 and 1 have none, with the arm-trunk contacts on). The trace adds `round` and `progress` (parts placed).
- `trajectory.npz` keeps pick and place's keys (`subtask` holds the phase names) plus `instruction`, `round`, `progress` and `task`, so `data.convert_expert_run` reads kitting runs; it takes each run's `instruction` from `summary.json` as the task.
- Reference check on wheel_robot_26.8.16_3 with the fixed IK seeds: `outputs/kitting_check_seeds_v1/`: 20/20 seeds, 120/120 parts, every seed on its first draw, 109.7–163.2 s, max penetration 0.15 mm, no collision, max limit error 0.08 mrad, parts within 0.45 mm of their cells, `data.subtask_check` passing on all 20 (14 single-arm subtasks each). ## Experiment rules

- Grasps must hold through contact and friction alone. Don't use any of these:
  - welds or attachment constraints
  - writes to object poses after reset
  - contact-mask changes at runtime
  - writes to the robot's qpos or qvel
- The gripper linkage's joint equalities (`sim/gripper_linkage.py`) couple robot joints to each other only, like URDF mimic joints. They are part of the mechanism, not grasp constraints, so the rule above still holds between the robot and the objects.
- Ground-truth object state is for the expert and for scoring only. It must never become a policy input.
- Episodes split into subtasks (user decision, 2026-10-25). A subtask is one action of one arm on one object: pick X, place X at Y, move the arm back, or one interaction such as opening a door or pressing a button. Its English text, naming the arm and the object, is the `instruction` of `Scene.stage(name, instruction)` and becomes the trace's `subtask`; the stage name stays the finer phase. While one arm works the other holds: its joint goals and gripper don't change. Both arms move in one subtask only when both hands act on one object, and then its text says "both hands". No two-arm starts or returns. `python -m data.subtask_check <run>` checks it on the trace.
- The training contract is 16-D (the full 22-D log above adds the waist and head), in this order:
  - left arm: 7 joint angles in radians, in `ARM_JOINTS` order
  - right arm: 7 joint angles
  - left gripper closure, then right (0 open, 1 closed). The two fingers get equal and opposite position targets of 0.0475·g m. Measured closure is (q1 − q2)/0.095.
- The leg stays upright (calf and thigh at 0), matching the lab robot photo. The user decided on 2026-10-24 not to adopt the Z-shaped crouch seen in the factory videos, so don't "fix" the posture unless asked.
- The chest carries the factory print: INOVANCE, "Powered by", FMC³ and ROBOTICS. On 2026-10-24 the user reversed an earlier choice of the lab robot's INOVANCE-only chest, so don't go back to it.
- The workspace layout is set by what the cameras can see. With the head pitched 0.50 rad, the head D435 sees the table only from about x=0.33 m, so pick and place's `SOURCES` are at x=0.38 and `GOALS` at x=0.40; IK fails beyond about x=0.45. If you move them closer, the head camera loses the workspace.
- Trajectories are raw expert captures, not LeRobot datasets; `data/` converts and exports them. Any export must keep the camera timestamps and the action semantics.
- `scene.xml` refers to meshes by absolute path, so it only loads in the checkout that wrote it: a run made on the pro6000 doesn't load here.

## SDK bridge (simbridge)

- Upper-level code talks only to the unmodified V1R1C9 SDK; `sdk.stock_sdk.connect(profile)` picks the target from `config/connections/*.yaml` (RK3588 or a simulator). Never edit anything under `sdk_review/feimi1010/sdk/`; `sdk/verify_backends.py` byte-compares it with `sdk.zip`.
- Layers, each importing only those below: `protocol` → `services` → `control` → `robot` → `runtime` → `backends/<engine>_backend.py`. Only adapters import an engine (a test enforces this), and the runtime runs the engine on the main thread; RPC threads use the command queue and snapshots, never the engine.
- SDK joint values are controller-MDH coordinates, `q_sdk = sign * q_urdf + offset`, from `config/robot/franzi_sdk.yaml` (both arms: sign +1 and offset 0 for every joint on wheel_robot_26.8.16_3, whose arm frames coincide with the controller's MDH frames; wheel_robot_4.0 had signs [-1, 1, -1, -1, -1, -1, 1]. From `sdk/check_sdk_kinematics.py` and `config/robot/kinematic_crosscheck.json`; not hardware-verified).
- `build_task.align_joint_limits` clips the MuJoCo joint ranges to the SDK limits in `config/robot/franzi_sdk.yaml` (URDF ∩ controller, with the 0.001 rad margin on the controller side). The MuJoCo adapter refuses to load if an engine range is wider than the URDF's or narrower than what the SDK layer accepts.
- `simbridge/backends/mujoco_backend.py` wraps `scenes.pick_place.run.PickPlaceScene`, so the bridge serves the pick-and-place scene (`goal`, `grip`, `physics_step`, `object_info`, `robot_bodies`, `maxdepth`); changing those changes the bridge.
- simbridge runs on MuJoCo only: the PyBullet backend was retired on 2026-10-24 (user decision; only the MuJoCo scene is aligned to the real robot). Its earlier results stay in `outputs/sdk_backends_v1`, `v6` and `v8`.
  - `sdk/convert_pybullet_assets.py`, which derived `assets/derived/pybullet/` (a URDF scene with MuJoCo's colliders) for the Isaac Sim draft (simbridge's never-run isaacsim backend) from wheel_robot_4.0's `franzi.xml` and URDF, was deleted with the migration (user decision 2026-10-25). The draft backend has no scene source until it gets one; the Isaac port (`isaac/`) builds from the compiled MuJoCo model instead.
- `config/sdk_acceptance/program.json` is generated by `sdk/make_sdk_program.py` from the expert run in `outputs/pp_seeds_rec/` (its default since the IK-seed fix; `outputs/pp_urdf_rec/` before it, `outputs/expert_wrist_block/` on wheel_robot_4.0); regenerate both when the task layout or the expert changes. `sdk/sdk_acceptance.py` refuses non-loopback hosts: its motions are simulation-only.
  - The generator slows any phase that exceeds 0.9× the SDK's planning-only rate limits (`config/robot_constraints/joint_limits.yaml`: 1 rad/s and 2 rad/s² per arm joint) and records the factor. The subtask expert's transfers slow ×1.17–1.20; each phase also names the arm that moves (`arms`).
  - `pose_a` is the expert's default posture (the first recorded tick). On wheel_robot_26.8.16_3 the straight joint line from the SDK zero pose to it puts the jaws into the table, so the program carries `lift_pose`, `Scene.lift_path`'s raised pose: every way between zero and the work poses (the core checks, the kinematics checks, Home, the task's start) goes through it, and the generator's sweep checks those lines.
  - The task check wants each lifting arm's gripper holding (2) after its lift, one arm at a time under the subtask rule.
- `simbridge/sdk_kinematics.py` answers Fk, FkTool, IK, FKb/IKb(Tool), Get/SetFlan2tool and GetCurCartesianPose(Dual) from `robot_kinematics`. It only converts SDK conventions:
  - SDK joint values via the active `UnitMap`.
  - Frames: A0 and the flange come from `kinematic_crosscheck.json`, and B is URDF `base_link`, the simulated robot's true pose.
  - Wire format: column-major 4x4 transforms at float32; poses are `[x, y, z, rz, ry, rx]` with `R = Rx Ry Rz`.
  - An unreachable IK target returns -6.
  - The IK emulates the controller's IK, which keeps no planning margin, but stays inside what MoveJ accepts: `Kinematics(margin=` the SDK position margin `+ 0.0001)`. The SDK layer keeps its 0.001 rad from the URDF bounds too, and wheel_robot_26.8.16_3's wrist roll stops at 1.57, inside the controller's 1.5708: with 0.0001 an IKb solution sat at 1.5698 and MoveJ rejected it (-3). `sdk.sdk_cartesian` uses the planning default.
  - The endpoints that only expose the controller's own model (FkLink, GetMdh, GetMdhCompensation, GetArmEulerAngle, SetMdh*) are unsupported, as are MoveL and Cartesian jog/teleop.
  - Without Pinocchio (the Isaac env) the server still starts and these endpoints report UNSUPPORTED.
  - The vendor manual's hard-coded FKb constants sit (0, ∓0.0725, −0.26355) m from the URDF chain at the upright stance, so the real controller's FKb likely differs from the simulation's. Real Cartesian goals belong on the host.
  - `sdk/check_sdk_kinematics.py` keeps the NumPy MDH-vs-URDF math, offline only. A test checks SDK Fk against the image's MDH chain to 2e-5 (wheel_robot_26.8.16_3's rounded right angles; 1e-12 on wheel_robot_4.0).
- `sdk.sdk_cartesian.CartesianArm(arm)` is the host-side way to reach Cartesian goals on sim and real alike. It solves with `robot_kinematics` (measured arm and waist joints, current orientation unless given) and sends SDK joints: `move()` as one MoveJ, `line()` through the joint teleop queue at 25 Hz.
  - `line()` slows down to stay within 0.9 of `GetJointVelLimit`.
  - Targets are `{side}_grasp` points in the simulation's world frame.
  - Keep it out of `sdk/stock_sdk.py`: the server's wire layer imports that module, and some server envs lack Pinocchio.
- Teleop playback paces each pushed point by the median of the session's last 50 push gaps (about 2 s), using the 40 ms default until 8 gaps are known. Gaps over 0.2 s count as pauses: they are left out without clearing the history.
  - A slow reply stalls the client, and its absolute schedule then sends the missed points back to back. The old median of 8 gaps, cleared at every pause, collapsed in those bursts, which PyBullet's GIL-holding steps made common.
  - The collapse drove playback into the velocity clamps and bent the hand path by up to 30 mm (the v7 PyBullet task failed).
- The MuJoCo adapter runs under `inovance-fineart` (`config/backends/mujoco*.yaml`, which name no interpreter: `verify_backends` starts the server under its own; the isaacsim one names `${ISAAC_PYTHON}`). It renders every image size through one shared GL/MuJoCo context: each context carries its own 8192² shadow map, about 256 MB. The pixels match `mujoco.Renderer`'s to within 1 level.
